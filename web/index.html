lang▌

a self-hosted compiler-compiler — many syntaxes, one binary

lang is a compiler whose real product is readers: syntax plugins, written in lang itself, that each turn a different surface language into one shared AST. Five languages ride it today — a C subset, a real Lisp, a coroutine DSL, a Forth, and an indentation-delimited Python subset — and because they all lower to the same AST, the same type system, and the same backend, they compose in a single native binary, calling each other directly. No FFI, no embedding API, no VM: a call from the Python subset into Forth is a call instruction.

Everything below was compiled to WebAssembly by lang’s LLVM backend and runs entirely in this page (view source: one small host shim, no libraries). Start with the polyglot tab — it is the whole point.

what a reader is

A reader is an ordinary lang function: source text in, AST out. This is the complete interface — the last four lines of the C reader: 

reader c(text *u8) *u8 {
    var t *Tokenizer = tok_new(text);
    var prog *PNode = parse_c_program(t);
    return emit_program(prog);
}

When the compiler meets a #c{ ... } block it builds the reader (once, cached), runs it at compile time on the block’s text, and splices the returned AST into the program as if you had written it in lang. By code generation there is no trace of which syntax anything arrived in — which is why cross-language calls are just calls, and why the whole five-language program can ship as one wasm module.

Readers are built from two tools. For parsing, #parser{ ... } takes a grammar and generates a recursive-descent parser (the parser generator is itself a reader — the mechanism is self-applicable). For output, std/ast.lang is a library of typed AST constructors (ast_func, ast_if, ast_binop, …). Here is the heart of the C reader’s grammar, verbatim: 

#parser{
    c_program  = c_topdecl+
    c_topdecl  = c_structdef | c_enumdef | c_topvar
    c_stmt     = c_retstmt | c_ifstmt | c_whilestmt | c_forstmt
               | c_switchstmt | c_breakstmt | c_continuestmt
               | c_decl | c_block | c_exprstmt
    c_ifstmt   = 'if' '(' c_expr ')' c_stmt c_elses
    c_expr     = c_binexpr c_terntail*
    c_terntail = '?' c_expr ':' c_expr
    c_binexpr  = c_unary c_oprest*
    c_oprest   = operator c_unary
    c_postfix  = c_primary c_postfixop*
    c_primary  = number | string | symbol | c_parenexpr
    ... (~65 rules total)
}

Note what the grammar does not do: operators are flat (c_oprest*), and precedence lives in the reader as ~40 lines of precedence climbing. That split is deliberate — the generated parser is a weak no-backtracking machine, so grammars are designed around a single rule (every alternative distinguishable by its first token) and the reader does the thinking. Crucially, readers live in example/, not in the compiler. The compiler has no idea C or Python exist.

five languages, five paradigms

#c{} — imperative · 840 lines

A genuine C subset: functions, structs, enums, pointers, arrays, strings, the full operator set including ternary, switch, for, compound assignment, ++. What the kernel lacks, the reader desugars: c?a:b becomes a value-returning block, ~x becomes x^-1, switch becomes an if/else chain, p->f is lexed as p.f and the kernel’s auto-deref does the rest. Deliberately bounded: no typedef, no preprocessor.

#minilisp{} — functional · 350 lines + a 200-line runtime

A real Lisp, not arithmetic-in-parentheses: boxed values, first-class cons lists, quote, let, lambda with closures, funcall/apply. It proved the pattern for languages that need a runtime: the runtime is just an included lang file, and boxing is an ABI — every Lisp value is an i64 that is really a pointer, so Lisp lists pass through C and Forth untouched.

#flow{} — coroutines · 380 lines

Generators: gen primes(n) { ... yield p; ... } and drivers with for x in g(n), lowering to lang’s algebraic effects. It is bidirectional — yield is an expression and the driver can send a value back into the suspended generator. flow proved a reader can surface kernel powers that no C-like syntax exposes. (It is the one absentee here: effects need stack switching, which core wasm doesn’t have, so flow is native-only and a plain lang loop holds its seat in the demo above.)

#forth{} — stack · 680 lines

The language furthest from the others: no expressions, no blocks, just words. The reader’s trick is that the data stack exists only at compile time, as a stack of AST nodes: dup * pops and pushes trees, and by ; the stack has vanished — : square dup * ; compiles to exactly the code of return n * n. The stack-effect comment ( n -- n2 ), decoration in real Forth, is load-bearing here: it names the parameters, which is what turns a word into an ordinary function that C and Lisp can call.

#minipy{} — layout · 950 lines

Blocks delimited by nothing but the left margin. The shared tokenizer is whitespace-blind and was not touched: tokens carry their byte offsets, so the reader reconstructs line starts and columns and synthesizes the NEWLINE/INDENT/DEDENT stream CPython’s own tokenizer feeds its parser. The offside rule — the thing that makes Python famously hard to bolt onto other grammars — turned out to be a plugin too.

In the polyglot demo they form one pipeline: minipy drives the survey and calls a lang loop, which asks C’s c_is_prime, which asks Forth’s divides? about every candidate divisor; each prime is consed onto a Lisp list; Lisp folds it; Forth digit-sums the result; minipy formats the report. Five paradigms, and no two of them agree on where a block ends — parens, braces, semicolons, then, and the left margin.

so how hard is it to add a language?

Each language above is one file (plus, at most, a small runtime file): 350–950 lines of lang against a ~2,400-line shared toolkit (tokenizer, grammar compiler, parser generator, AST builders). None of them required changing the compiler. Across all five, the shared tokenizer gained two token kinds (? ~), a few two-character operators, and comment skipping — everything else, including Python’s indentation, was reader-side.

The recurring surprise was how rarely a “new language feature” needed anything new underneath. The kernel keeps being richer than any one syntax: ternary needed no conditional-expression node, enum members are just globals, Lisp lambdas ride the kernel’s closures, and flow — the most exotic of the five — needed zero new kernel features. The honest costs are elsewhere: languages with real semantics need a small runtime built (Lisp’s boxing, cons cells and closures came to 200 lines); C’s typedef needs the classic lexer hack and the preprocessor is its own project; and paradigm distance costs thought rather than lines — Forth and Python were the hardest to capture and the most fun, precisely because neither looks anything like the AST it lowers to.

wrap a reader, get a compiler

So far the languages have lived inside #c{ ... } blocks in a lang file. They don’t have to. The compiler is really two parts: a kernel — AST in, native code out, no surface syntax at all — and a reader bolted onto the front. lang’s own syntax is just the reader that ships by default; every bootstrap rebuilds the compiler as kernel + lang-reader and verifies the composition to a fixed point.

The -r flag performs the same bolting for any reader: emit the reader’s AST once, compose, and out comes a new native binary that compiles that reader’s language directly — whole files, not blocks. This transcript is real: 

$ lang --emit-expanded-ast example/c/c.lang -o c_reader.ast
$ kernel -r c c_reader.ast -o cc.ll   # compose: kernel + C reader
$ clang -O2 cc.ll -o cc

$ cat fib.c
int fib(int n) {
    if (n < 2) return n;
    return fib(n - 1) + fib(n - 2);
}
int main() { return fib(10); }

$ ./cc fib.c -o fib.ll                # a standalone C compiler
$ clang -O2 fib.ll -o fib && ./fib; echo $?
55

That cc is a real executable: it dispatches .c files to the C reader by extension, never sees a line of lang, and its 55 came through the same kernel that compiled everything else on this page. This is the literal sense in which lang is a compiler-compiler: it compiles readers, and a reader wrapped around the kernel is a compiler. A grammar and a lowering pass are the whole cost of a new compiled language — the kernel supplies the backend, and -r gives the language a front door of its own.
