# 0024: Forth, and the Stack That Isn't There

**Date:** 2026-08-01

## Summary

A fourth language: **Forth**. It's the first one that isn't C-shaped underneath — C, minilisp and flow all have an expression grammar, and Forth has none at all. A Forth program is a flat stream of whitespace-separated words operating on a data stack, and control flow is just more words.

The interesting part is that **the generated code has no stack in it**. The reader keeps a stack of *AST nodes* while walking the word stream: `dup` duplicates a node, `*` pops two and pushes `(binop * a b)`. By the time `;` arrives, the stack holds the word's result and every trace of it is gone.

```forth
: square ( n -- n2 ) dup * ;
```

compiles to exactly what hand-written lang would produce — at `-O0` the same load/load/mul as `return n * n;`, and once optimized:

```llvm
define i64 @square(i64 %n.arg) local_unnamed_addr {
L.entry:
  %t2 = mul i64 %n.arg, %n.arg
  ret i64 %t2
}
```

This mirrors how a real Forth compiles `if`/`then` with a compile-time control stack — we just erase the data stack too.

## The stack effect earns its keep

In real Forth, `( n -- n2 )` is a comment. Here it's load-bearing: it names the parameters and counts the results, which is exactly what's needed to turn a word into an ordinary i64 lang function with a normal signature. That's what lets C, Lisp, flow and lang call a Forth word — and lets Forth call them back, via `extern name ( a -- r ) ;`.

## Lazy nodes are a lie you have to pay for

A stack of *unevaluated* AST nodes is only a legal model of Forth if pending computations are forced at the right moments. Two ways it goes wrong:

- **Duplication.** `dup` copies a value, not a computation. If the top of stack is `noisy(3)` and you just push the node twice, you get `noisy(3) * noisy(3)` — the call runs twice.
- **Reordering.** `1 noisy 42 . ` must print `<1>` before `42`. If `noisy(1)` is still an unevaluated node when the `.` emits its print statement, the print lands first and the side effects come out backwards.

Both are fixed by the same rule: before any word that duplicates, reorders, discards or emits a statement, flush the stack — materialize every non-simple node into a temp, bottom-up, so it happens *here*. Numbers and bare identifiers are exempt, which is why `n dup *` still costs nothing. Dropping a value flushes too, because in Forth the dropped value was still computed.

The test file checks all four cases and prints markers so the order is visible rather than asserted.

## No grammar, on purpose

The `#parser{}` grammar for Forth is nearly empty — a body is just `fo_word*`, a flat list. `if`, `else` and `then` are handled by the converter walking that list with an index, exactly as Forth's immediate words do. That's authentic *and* it sidesteps the weak no-backtrack parser completely: there's no nesting for it to get wrong.

`if`/`else`/`then` reconciles by running both branches over a copy of the same stack and comparing them slot by slot. Any slot they disagree about becomes a temp assigned in both branches — which is how a value-producing conditional falls out of a language with no conditional expression:

```forth
: fact ( n -- f ) dup 2 < if drop 1 else dup 1 - recurse * then ;
```

## The bug this found

Forth is the first reader to use `continue` — and it segfaulted, while the *identical source compiled standalone* was correct. That's a nasty shape for a bug.

A reader's source is regenerated by unparsing its AST back to lang source before being compiled in a forked child. `ast_to_string_stmt` had cases for var/return/expr/assign/if/while/block — and nothing else, falling through to a `/* unknown stmt */` comment. So `continue` was **silently deleted**, and control fell through into the code it was supposed to skip. No error, no warning; the reader just computed the wrong thing and then walked off the end of a node.

Fixed by adding `break`/`continue` (with labels), emitting the loop label the `while` case was also dropping, and making the fallback print an error instead of quietly discarding a statement. Regression test: `test/suite/154_reader_break_continue.lang` (returns 0 on the old compiler, 42 on the fixed one).

No shipped reader used `break` or `continue`, so nothing was broken in practice — it was waiting for the first reader author who reached for either.

## In the polyglot

Forth doesn't sit off to the side. `divides?` is the innermost step of the sieve, so C's trial-division loop calls it; and `digit_sum` recurses over the sum Lisp computes at the far end. The call chain now crosses all four languages in one direction of travel — flow → C → forth — before coming back out through Lisp.

```
=== prime pipeline: flow -> C -> Lisp ===

primes <= 30 (Lisp list) = (29 23 19 17 13 11 7 5 3 2)
count (Lisp ml_len)      = 10
sum   (Lisp ml_sum)      = 129
count (flow count_primes)= 10
digits(sum) (forth)      = 12

POLYGLOT PASS
```

## Bounds

Recursion is the only repetition — no `begin`/`do` loops and no `variable`/`!`/`@` yet, which keeps a word body a pure expression tree. Adding mutation is the interesting next step, because it's the thing that makes the compile-time-stack model actually hard. Word names are lang identifiers plus an optional trailing `?` (`prime?` mangles to `prime_p`), since the shared tokenizer lexes `-` as an operator. Negative literals must be written `0 5 -` or `5 negate`.

Comments needed one real fix: a Forth comment may contain anything, but the shared tokenizer chokes on a `:` or a quote inside one. Since the stack effect wears the same parentheses and *is* parsed, the reader sanitizes every parenthesized interior down to word characters before tokenizing — comments can say what they like, stack effects still read.
